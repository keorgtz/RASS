Problema resuelto

Al configurar un SDD ModeProfile, el usuario podía elegir un modelo pero no el proveedor. El modelo se almacenaba como string provider/model (ej. opencode-go/glm-5.1), pero el provider venía implícito en el ID — no había forma de:

  • Validar que un modelo pertenece a un provider antes de guardar.
  • Forzar que un perfil use siempre un provider específico.
  • Usar modelos custom (opencode-go/experimental-model) que aún no están en el catálogo.
  • Mezclar modelos de distintos providers en un mismo ModeProfile de forma explícita.

Solución implementada

Selección en dos pasos (Proveedor → Modelo) en el TUI, con opción Custom model para strings manuales, y un nuevo argumento provider en el tool con validación.

Antes (un solo paso, lista plana)

Configure models for "my-profile" — Single model for all phases ✓ GLM-5.1 Kimi K2.7 Code DeepSeek V4 Pro ...

Después (dos pasos + custom)

Select provider for "my-profile" — Configure models OpenCode Go (6 models) ← current Anthropic (3 models) OpenAI (3 models) Google (2 models) + Custom model (provider/model) ← Back OpenCode Go — Select model for "my-profile" ✓ GLM-5.1 reasoning Kimi K2.7 Code coding DeepSeek V4 Pro reasoning ... + Custom model (provider/model) ← Back to provider list

.opencode/plugin.js +85 líneas

Nuevo argumento opcional provider en sdd_mode_profile (action=create/edit):

  • provider + primary → valida que primary.startsWith(provider + '/'), error si no coincide.
  • provider solo → resuelve al primer modelo del provider.
  • primary solo → backward compatible, acepta cualquier string.
  • ninguno → default a opencode-go/glm-5.1.

El output de list, switch, edit, create, status ahora muestra el provider derivado del default model.

Ejemplos de uso

Tool sdd_mode_profile

// Forzar que el primary sea de opencode-go (valida)
sdd_mode_profile(action="create", name="fast-test",
  phases="orchestrator,apply,verify",
  primary="opencode-go/kimi-k2.7-code",
  provider="opencode-go",
  effort="medium")
→ OK, no warning

// Custom model del provider opencode-go (warning, no error)
sdd_mode_profile(action="create", name="experimental",
  phases="orchestrator",
  primary="opencode-go/experimental-v1",
  provider="opencode-go")
→ OK, warning: "Model 'experimental-v1' not in catalog of 'opencode-go' (custom)"

// Mismatch → rechazado
sdd_mode_profile(action="create", name="bad",
  phases="orchestrator",
  primary="anthropic/claude-sonnet-4-5",
  provider="opencode-go")
→ Error: "Primary model 'anthropic/claude-sonnet-4-5' does not belong to provider 'opencode-go'"

// Provider solo (sin primary) → usa primer modelo del provider
sdd_mode_profile(action="create", name="anthropic-only",
  phases="orchestrator,apply",
  provider="anthropic")
→ Resuelve a "anthropic/claude-sonnet-4-5" (primer modelo)

// Backward compatible: solo primary (sin provider)
sdd_mode_profile(action="create", name="legacy",
  phases="orchestrator",
  primary="opencode-go/glm-5.1")
→ OK, sin validación

Decisiones de diseño

  • Formato canónico en disco sin cambios: el modelo sigue siendo string provider/model. No se introduce objeto {provider, model}.
  • El provider es opcional, no obligatorio: si un ModeProfile existente no especifica provider, sigue funcionando idéntico.
  • El catálogo viene del runtime de OpenCode (api.state.provider): no se mantiene una lista paralela hardcoded en RASS.
  • Custom model es first-class: los modelos no listados se aceptan con warning, no error. Cubre providers beta, modelos nuevos y providers privados.
  • Cross-platform trivial: api.state.provider es idéntico en Windows y Linux (objeto JS). No se introduce código platform-specific.
  • Validación solo cuando se pide: validateModelInProvider solo se ejecuta si el usuario pasa provider. Sin provider, el comportamiento es idéntico al anterior (compatibilidad).
