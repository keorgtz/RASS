Problema reportado

El usuario agregó el soporte de proveedores en REASP (sesión 3) y reinstaló globalmente con npm install -g reasp-cli-1.0.0.tgz, luego corrió reasp install en sus agentes. Después de la reinstalación, las funciones nuevas no aparecían: el tool sdd_mode_profile no aceptaba el argumento provider, y los archivos en ~/.config/opencode/ seguían siendo la versión antigua.

Diagnóstico

El código en el repo REASP/.opencode/ tenía el soporte de proveedores correctamente implementado (DEFAULT_PROVIDERS, discoverProviders, validación, etc.). Los tests pasaban. El problema era de distribución y de PATH:

  1. Tarball desactualizado: reasp-cli-1.0.0.tgz se había generado el 08/07 antes de que se terminaran los cambios de proveedores el 09/07. El .tgz no contenía DEFAULT_PROVIDERS ni discoverProviders.
  2. Tres instalaciones simultáneas en el sistema:
    • C:\Program Files\REASP\ — instalación antigua con prioridad en el PATH (porque C:\Program Files\ está antes que %APPDATA%\npm). Cuando el usuario ejecutaba reasp, se llamaba a C:\Program Files\REASP\reasp.ps1, que ejecutaba la versión antigua.
    • C:\Users\kevin\AppData\Roaming\npm\node_modules\reasp-cli — instalación global correcta de npm, pero sin prioridad en el PATH.
    • C:\Users\kevin\KeorSoft\Development\AITools\REASP — repositorio de desarrollo, fuente de verdad.
  3. Hash mismatch: después de hacer sync-reasp.js push desde el repo, ~/.config/opencode/rass-core.js quedaba con el hash nuevo (43C6…). Pero al ejecutar reasp install, el archivo volvía al hash antiguo (E29C…). El culpable era la instalación antigua en C:\Program Files\REASP\ que sobrescribía los archivos del agente con la versión vieja.

Solución aplicada

Endurecimiento adicional aplicado en el código

  • package.json y installer/lib/constants.js suben a 1.0.1 para que reasp --version evidencie la actualización real.
  • Nuevo installer/scripts/postinstall.js: detecta si Windows resuelve reasp hacia una instalación vieja antes del shim npm, intenta actualizar la instalación standalone si tiene permisos, y si no, muestra una advertencia accionable.
  • El adapter de OpenCode ahora reemplaza directorios/archivos REASP-managed antes de copiarlos, evitando archivos obsoletos que ya no existan en el repo.
  • Los agentes REASP-managed en opencode.json se reemplazan completos en cada reinstalación, no solo el campo model. Así se actualizan prompts, permisos, steps y futuros cambios de schema.
  • model y small_model raíz ahora se re-sincronizan con el ModeProfile en cada instalación.
  • Nuevo scripts/check-syntax.js para que npm test sea cross-platform; los globs anteriores fallaban en Windows PowerShell/CMD.

Follow-up: comando /share de OpenCode no aparecía

  • Se verificó que OpenCode 1.17.17 sí contiene los comandos nativos /share y /unshare, y que la config no tenía "share": "disabled".
  • La causa probable es que el plugin TUI de REASP usa el API legacy api.command.register(); en esta versión del TUI esa lista puede dejar fuera comandos nativos del selector.
  • Se añadieron puentes explícitos en .opencode/tui.js para /share y /unshare, delegando al comando interno nativo de OpenCode: session.share y session.unshare.
  • Se sincronizó el plugin instalado en ~/.config/opencode/tui.js y se verificó sintaxis con npm test.

Sesión 5 — REFI v2 · Epic + PART Methodology

Upgrade del planner REFI: las fases como concepto top-level se reemplazan por EPICs (subsistema/capacidad) y cada EPIC contiene PARTs (15 secciones + 8 puertas mecánicas). El planner ahora espera al usuario en 2 puntos antes de avanzar a código. Backward-compatible con los 4 paquetes legacy existentes.

Problema resuelto

El método REFI v1 trabajaba con "shards" planos de 7 secciones. Para una sola fase, el planner pasaba a implementación sin esperar al usuario. No había anclaje contra realidad en los shards (§3 ausente), no había gates mecánicos verificables (5 viñetas genéricas), y no había forma de decir "ya planeamos TODO, ahora sí ejecuta". Esto provocaba:

  • Implementación prematura con código todavía por afinar.
  • Alucinaciones sin ancla contra archivos/líneas reales.
  • Criterios de "done" subjetivos (no testeables).
  • Re-planning a media ejecución.

Solución aplicada — metodología Epic + PART

Workflow de 3 pasadas (con 2 STOP gates de usuario)

Ryou EFI Planner │ ├─ Pass 1 — Epic Breakdown │ ├─ request.md │ ├─ master-blueprint.md (con EPIC breakdown) │ ├─ epics/matrix.md │ └─ epics//README.md (backlog × N) │ ⤷ STOP · WAIT FOR USER ⤷ ← Gate A │ ├─ Pass 2 — PART Detail (per EPIC, on demand) │ └─ epics//parts/PARTnn.md (15 sec + 8 gates footer) │ ⤷ STOP · entre EPICs ⤷ ← Gate B │ └─ Pass 3 — Orchestration & Hand-off ├─ orchestration-map.md ├─ progress.md ├─ verification.md ⤷ HANDOFF TO ORCHESTRATOR ⤷

Las 8 puertas mecánicas (strict order 1→8)

  1. Architecture Review — diseño vs invariantes / ADRs del proyecto.
  2. Scope & Completeness Audit — tabla declared vs actual, gaps clasificados.
  3. UX/Design Review — MeridianUI si UI; contratos si no UI.
  4. Manual / Runtime Validation — checklist §12 ejecutado con tickboxes.
  5. Defect Closure — todo defecto de gates 1–4 cerrado en el mismo PART.
  6. Technical Documentation — docs técnicos producidos.
  7. User Documentation — docs de usuario producidos.
  8. Final Review & Sign-off — build 0/0 + suite verde + Acceptance Criteria re-leído + firma.

Decisiones técnicas clave

  • RASS phases se preservan intactas. El Epic/PART es la capa externa (planeación). Las fases RASS son la capa interna dentro de cada PART durante ejecución. Complementary layers.
  • ModoProfile no se toca. Las 8 ModeProfiles (Fast, Architecture, UI, Debug, Enterprise, Legacy, Minimal, RyouSet) siguen eligiendo qué fases RASS se ejecutan dentro de cada PART.
  • Backward-compat por default. Los 4 paquetes legacy (reasp-backup-manager, linux-compat, multi-agent-compatibility, sdd-profile-provider-support) siguen funcionando — el flag epic_part.legacy_domain_shards_fallback: true los acepta sin tocarlos.
  • Helper de migración = opcional. El usuario decide por paquete; nunca auto-migración silenciosa. El helper crea un nuevo folder <slug>-v2/ y nunca toca el original.
  • Anti-hallucination reforzado en §3 y §15. §3 obliga ancla contra archivos/líneas reales del repo. §15 obliga bullets testeables. Frases como "industry standard" o "improve performance" sin medida son rechazadas.

Cómo se usa ahora (flujo de usuario)

1

2
El planner produce Pass 1: request.md, master-blueprint.md, epics/matrix.md, y 1+ READMEs de EPIC. Se detiene.
3
El usuario responde: "Detalla los PARTs del EPIC 01" o "Detalla TODOS".
4
El planner produce Pass 2: los PARTs (15 secciones + footer de 8 puertas). Se detiene.
5
El usuario confirma → Pass 3: orchestration-map.md, progress.md, verification.md. Hand-off literal a Ryou Orchestrator.
6
Orchestrator ejecuta EPIC por EPIC, PART por PART, gate por gate. Al cerrar las 8 puertas firma el footer del PART.

Anti-patterns evitados explícitamente

  • ❌ Implementación mientras los PARTs aún están en backlog.
  • ❌ Saltarse una gate para llegar a la siguiente.
  • ❌ Cerrar un PART con Acceptance Criteria no testeables.
  • ❌ Auto-migrar paquetes legacy sin pedirlo.
  • ❌ Acceptance Criteria vagos tipo "código limpio" o "se ve bien".
  • ❌ Inventar archivos, endpoints, servicios o columnas.

Problema resuelto

El usuario quería que REFI v2 Epic + PART estuviera disponible, pero sin romper el flujo actual. La metodología anterior (domain-shards por fases) debía seguir siendo el default, y Epic + PART debía ser seleccionable explícitamente desde la interfaz.

Solución aplicada

1. Estado persistente

  • .opencode/reasp.config.json añade "planning_method": "phases".
  • .opencode/rass-core.js añade VALID_PLANNING_METHODS, DEFAULT_PLANNING_METHOD, getPlanningMethod() y setPlanningMethod(method). Fallback seguro a "phases" si el campo falta o es inválido.
  • getReaspStatus() expone planning_method en su respuesta.

2. Tool programático

  • .opencode/plugin.js: reasp_setup acepta action="set-planning-method" con argumento method (phases o epic).
  • La acción status devuelve el método activo.

3. TUI /reasp-setup

  • .opencode/tui.js: nueva opción "Switch Planning Method" con sub-selección Phases (legacy) / Epic + PART (v2).
  • El toast de View Status muestra el método activo.

4. Prompt dual del planner

  • .opencode/agents/ryou-efi-planner.md reescrito como dual-mode. Al inicio de cada sesión el agente debe llamar reasp_setup(action="status") y seguir la sección correspondiente (phases o epic).
  • Se preservan Gate A, Gate B y Handoff literal para Epic + PART; se añade Gate y Handoff literal para Phases.

5. Documentación

  • README.md (raíz): se explica que Phases es default y Epic + PART es opt-in; se documenta reasp_setup(action="set-planning-method", method="...").
  • .opencode/refi/README.md: sección "Planning Method Selector" con tabla, ejemplos de uso y nota de que ryou-efi-planner.md detecta el modo al inicio.

6. REFI packet EPIC 08

  • .refi/modules/refi-epic-part-methodology/epics/08-planning-method-selector/: README + 3 PARTs (08-01-config-state, 08-02-tool-and-tui, 08-03-dual-prompt).
